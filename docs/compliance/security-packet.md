## 1. Architecture Summary

Operious AI is a multi-tenant AI customer-support platform. The production deployment runs on Fly.io (app `operious-ai-imad`, region `iad`) and consists of:

| Component | Technology | Role |
|---|---|---|
| API server | FastAPI (Python) | HTTP/WebSocket; middleware stack enforces auth, rate-limits, tenant isolation |
| Database | Neon PostgreSQL | Durable storage; Row-Level Security on every tenant-scoped table |
| Task workers | Celery (8 process groups) | Async diagnostic, escalation, supervisor, SME-approval, SOP, maintenance, ingress, outbound-send, and voice-realtime queues |
| Message broker | Redis / CloudAMQP RabbitMQ | Celery broker and result backend |
| Cache / rate-limit store | Upstash Redis | Fixed-window rate-limit counters, idempotency keys, governance policy pub/sub |
| Authentication | Auth0 (`operious-dev.uk.auth0.com`) | JWKS-signed RS256 JWTs; custom namespace `https://operious.com` |
| LLM inference | AWS Bedrock (region `us-east-1`) | Claude Haiku / Sonnet via Anthropic inference profiles; no customer data is sent to the direct Anthropic API in production when `LLM_PROVIDER=bedrock` |
| Embeddings | OpenAI | `text-embedding-3-small`, 1536-d |
| Key custody | GCP Cloud KMS (`CREDENTIAL_KMS_BACKEND=gcp`, `DATA_PROTECTION_KMS_BACKEND=gcp`) | Wraps data-protection master key ring; key material never stored in plaintext at rest |
| Attachment storage | AWS S3 | Customer-submitted files; app-layer AES-256-GCM envelope wraps every object before upload |
| Error tracking | Sentry | `SENTRY_SEND_DEFAULT_PII=false`; PII scrubbing enabled |

Secrets (`AUDIT_EXPORT_HMAC_SECRET`, `TENANT_CREDENTIAL_MASTER_KEY`, all provider credentials) are set via `fly secrets set` and are never committed or present in `fly.toml`.

## 2. Data Flow

```
Customer channel (email / WhatsApp / Shopify / voice)
  │
  ▼
Ingress worker (HMAC-verified webhook or signed session token)
  │
  ▼
Boundary layer  ─────── translation (if multilingual) ─────────
  │                                                             │
  ▼                                                             │
Session record (Neon, RLS-scoped to tenant)                     │
  │                                                             │
  ▼                                                             │
Diagnostic queue (Celery: diagnostic.high / .normal / .retry)  │
  │                                                             │
  ▼                                                             │
Diagnostic cognition (AWS Bedrock)                             ◄┘
  │  ──── prompt + completion written to cognition_audit_records (encrypted)
  ▼
Governance layer (capability check → allow / require-approval / deny)
  │
  ├─── ALLOW:  resolution applied; outbound reply enqueued
  ├─── APPROVAL REQUIRED:  SME-approval queue; human action via Command Center
  └─── DENY:   escalation queue; operator notified
```

Every Neon query runs as role `operious_app` (`BYPASSRLS=False`). Session-config variable `app.current_tenant_id` is set per-request by the application layer; the `operious_tenant_rls_allows()` policy function enforces it on every tenant-scoped table before any data is returned.

## 3. Tenant Isolation

### 3.1 Database (PostgreSQL RLS)

All tenant-scoped tables have `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`. The application role `operious_app` has `BYPASSRLS=False` (verified live in S-10 evidence `2026-07-05-rls-pass.json`). The policy on every table is:

```sql
USING (operious_tenant_rls_allows(tenant_id))
WITH CHECK (operious_tenant_rls_allows(tenant_id))
```

Tables covered include (non-exhaustive): `operational_sessions`, `session_events`, `execution_records`, `dead_letter_tasks`, `provider_quota_records`, `cognition_audit_records`, `webhook_nonce_records`, `data_protection_data_keys`, `data_protection_legal_holds`, `data_protection_erasure_requests`.

### 3.2 Application-Layer Envelope Encryption

`DataProtectionService` (`app/data_protection/crypto.py`) implements a two-level key hierarchy:

- **Master key ring** (`MasterKeyRing`): versioned platform keys (`DATA_PROTECTION_MASTER_KEYS`), unwrapped from GCP KMS when `DATA_PROTECTION_KMS_BACKEND=gcp`. Key material is never stored in plaintext at rest.
- **Per-scope data keys**: 256-bit random DEKs generated by `os.urandom(32)`, wrapped under the master key using AES-256-GCM with authenticated additional data binding tenant, scope, scope-id, and key version.
- **Sensitive JSON fields** encrypted individually (list in `_SENSITIVE_JSON_KEYS`: `body`, `content`, `customer_message`, `transcript`, `text`, etc.).
- **LLM prompts and completions** stored as encrypted `LargeBinary` in `cognition_audit_records.prompt_full` / `completion_full`.
- **Attachment bytes** encrypted by `DataProtectionService.encrypt_bytes` before upload to S3.

DSAR erasure deletes the DEK row, making all ciphertext associated with that subject permanently unreadable ("crypto-erasure").

### 3.3 Identity Namespace Binding

Auth0 custom claims are namespaced under `https://operious.com` (configured in `AUTH0_NAMESPACE`). The `tenant_id` claim is `https://operious.com/tenant_id`; it is extracted from the verified JWT, never accepted from a client-supplied header in production (`LEGACY_HEADER_AUTHORITY_ENABLED=false` in production).

## 4. Authentication and Authorization

### 4.1 Auth0 JWKS Verification

Production configuration (set in `fly.toml`):

```
AUTH_PROVIDER=auth0
AUTH0_DOMAIN=operious-dev.uk.auth0.com
AUTH0_ISSUER=https://operious-dev.uk.auth0.com/
AUTH0_AUDIENCE=https://api.operious.ai
AUTH0_JWKS_URL=https://operious-dev.uk.auth0.com/.well-known/jwks.json
```

The `JWKSAuthProvider` verifies every Bearer token against the JWKS endpoint using PyJWT with `algorithms=("RS256",)`. Signature, issuer, audience, and expiry are all checked. Failed verification returns a coarsened 401 in production (`COARSE_AUTH_ERRORS=true` effective in production) so error detail cannot aid reconnaissance.

### 4.2 Domain Capabilities (RBAC)

The `PERMISSION_CAPABILITY_MAP` and `ROLE_CAPABILITY_MAP` in `app/auth/providers/jwt.py` map Auth0 permissions and roles to internal capabilities. The full capability surface (from `app/dependencies/authority.py`):

| Capability | Purpose |
|---|---|
| `tenant.config.read` | Read the config change-request ledger |
| `tenant.config.write` | Propose config changes |
| `tenant.config.approve` | Approve/apply config changes (separation of duties from write) |
| `tenant.connector.read` | Read connector configuration |
| `tenant.connector.write` | Propose connector changes |
| `tenant.connector.approve` | Approve connector changes (distinct role from write) |
| `tenant.channel.admin` | Mutate channel configuration |
| `tenant.knowledge.write` | Mutate knowledge documents |
| `tenant.policy.write` | Mutate governance policies |
| `tenant.topology.write` | Mutate topology configuration |
| `tenant.execution_governance.write` | Mutate execution-governance configuration |
| `tenant.observability.read` | Read metrics, DLQ, alerts, SLOs |
| `tenant.audit.export` | Export signed audit records |
| `tenant.actions.approve` | Approve/reject agent operational actions |
| `tenant.approvals.read` | Read SME approval queue |
| `tenant.resolution.guide` | Guide resolution re-proposals |
| `tenant.training.write` | Mutate trainer recommendations |
| `tenant.privacy.admin` | Administer legal holds, retention policy, erasure proposals |
| `tenant.privacy.approve` | Approve irreversible erasures (dual-control from admin) |
| `platform.tenant.admin` | Platform-level tenant lifecycle administration |
| `operator` | Broad read-only operations access |

Every HTTP endpoint declares its capability requirement as a FastAPI `Depends(require_<capability>)`. A spoofed `X-*-ID` header carries no capabilities and cannot satisfy any capability gate.

### 4.3 Trusted-Ingress Chain

In production, `TRUSTED_PROXIES=fdaa::/16` restricts authority-bearing requests to those forwarded by the Fly.io edge proxy. Direct callers cannot stamp `X-Tenant-ID` headers (S-01). Evidence: `2026-07-05-spoofing-pass.json`.

### 4.4 Rate Limiting

Three-layer fixed-window rate limiting on Redis (production-only by default):

- **Per-IP** (pre-auth): 120 req/min — `EdgeRateLimitMiddleware`
- **Per-tenant** (post-auth): 600 req/min — `TenantRateLimitMiddleware`
- **Per-principal** (post-auth): 300 req/min — `TenantRateLimitMiddleware`

Health/liveness/readiness probe paths are exempt.

## 5. Security Controls

| Control | Implementation |
|---|---|
| **SSRF guard** | All outbound webhook/connector URLs are validated: HTTPS required, private/loopback/reserved addresses blocked, host allowlist enforced (`OUTBOUND_WEBHOOK_ALLOWED_HOSTS`). WhatsApp Graph API pinned to `graph.facebook.com`. |
| **Webhook HMAC** | Inbound webhooks (Shopify, WhatsApp) verified by HMAC before enqueue. Fulfillment callbacks have a per-connector `callback_hmac_secret`. Nonces stored in `webhook_nonce_records` with RLS; TTL-pruned after 24 h. |
| **Request body limit** | 1 MiB ceiling on all inbound requests (`RequestBodyLimitMiddleware`; `SURVIVABILITY_REQUEST_BODY_MAX_BYTES=1_000_000`). |
| **Voice WebSocket bounds** | Per-frame 64 KiB limit, 100 000 frames/call max, 3600 s wall-clock max, 30 s idle timeout, 100 fps rate cap. |
| **DLQ and dead-letter** | Unrecoverable tasks route to a dead-letter queue; `worker_maintenance` runs DLQ replay. Spike detection alerting via `AlertEvaluator`. |
| **Audit export HMAC** | Signed audit exports via HMAC-SHA256 (`AUDIT_EXPORT_HMAC_SECRET`, set via `fly secrets set`). |
| **Governance fail-closed** | Finance/goods actions (`MONEY`/`GOODS`) with no configured connector ledger return a governed error, never fake success, in production. |
| **CORS fail-closed** | `CORS_ALLOW_ORIGINS` must be an explicit allowlist; wildcard `*` rejected at boot. Production origins: `app.operious.com`, `www.operious.com`, `operious.com`, `platform.operious.com`. |
| **OpenAPI hidden** | `/docs`, `/redoc`, `/openapi.json` are disabled in production (`docs_url=None`). |
| **Production boot gate** | `validate_production_config()` runs at boot in production; refuses to start with stubbed providers, missing security secrets, or misconfigured auth. |
| **Structured JSON logging** | All processes emit JSON logs in production (`LOG_JSON=true`). Sentry `send_default_pii=false`. |
